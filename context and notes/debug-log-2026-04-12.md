# Debug Investigation: Logging + Search Failures — 2026-04-12

## Symptoms Reported
1. Dev panel at `/dev` shows 0 log entries
2. Search process does not return products in the browser

## Investigation Trajectory

### Step 1: Test endpoints directly via curl
- `POST /api/clarify` — returned 200 with questions + sessionId. Works.
- `GET /api/dev/logs` — returned `{"logs":[],"count":0}`. Broken.
- `GET /dev` — returned 200. Page loads.
- `POST /api/recommend` — returned SSE stream with products. Works at API level.

### Step 2: Check file logs on disk
- `logs/2026-04-12.jsonl` has **34 entries** across 7 sessions — file logging works fine.
- Every API call (clarify + recommend) correctly wrote search_query, ai_input, ai_output entries.
- Conclusion: `log()` function runs correctly. The issue is in `getLogs()` / in-memory retrieval.

### Step 3: Check server console
- Found `ERR_INVALID_STATE: Controller is already closed` error in recommend route.
- The catch block at line 274 tries to `controller.enqueue()` after the controller was already closed.

### Step 4: Trace the in-memory buffer isolation
- `logBuffer` is a module-level `const` array in `lib/logger.ts`.
- Next.js App Router compiles each API route as a **separate module bundle** (visible in server output: "Compiled /api/clarify in 730ms (801 modules)", "Compiled /api/dev/logs in 420ms (739 modules)").
- Each compilation creates its own module instance. The `logBuffer` in the clarify route's import of logger.ts is a **different array** from the one in the dev/logs route's import.
- File logging uses `appendFile` which writes to the shared filesystem — this works across module boundaries. But the in-memory buffer does not.

### Step 5: Trace the search result failure in the browser
- File logs show user session `7c3120e8` completed successfully: clarify (6 seconds) + recommend (49 seconds), no errors.
- The API returned real products. So why does the browser not show them?

**Found the critical bug in `page.tsx:162`:**
```javascript
// If we never got a result event, something went wrong
if (products.length === 0 && !summary) {
    throw new Error("No results received");
}
```
`products` and `summary` are **React state variables** captured by the `useCallback` closure. React state updates via `setProducts()` and `setSummary()` are asynchronous — they don't mutate the closure's captured values. Inside this callback, `products` is always `[]` and `summary` is always `""` (the values from when the closure was created).

**Result:** Every successful recommend request also triggers this check, which always evaluates to `true`, throws "No results received", and the catch block overwrites real products with fallback data. The user sees fallback products and a toast error "AI is temporarily unavailable."

## Bugs Found (3)

### Bug 1: In-memory log buffer not shared across routes (LOGGING BROKEN)
- **File:** `lib/logger.ts:7`
- **Cause:** `const logBuffer: LogEntry[] = []` is module-scoped. Next.js creates separate module instances per route. The `/api/dev/logs` route reads from its own empty buffer.
- **Fix:** Use `globalThis` to store the buffer as a cross-module singleton.

### Bug 2: Stale closure overwrites real products with fallbacks (SEARCH BROKEN)
- **File:** `app/page.tsx:162-164`
- **Cause:** `products.length === 0 && !summary` checks React state inside an async callback. React state updates are async — the closure always sees the stale initial values.
- **Fix:** Use a local `let gotResult = false` variable inside the callback, set it to `true` when the result event is parsed, and check that instead of React state.

### Bug 3: Controller double-close crash in recommend route
- **File:** `app/api/recommend/route.ts:274`
- **Cause:** When an error occurs after the stream was already closed (e.g., client disconnect during the 50-second Claude call), the catch block tries to `controller.enqueue()` and `controller.close()` on an already-closed controller.
- **Fix:** Added `safeEnqueue()` and `safeClose()` wrapper functions with a `streamClosed` flag. These delegate to `controller.enqueue()` and `controller.close()` only when the stream is still open.
